# Live link plan

The submission form wants a live working link and allows no resubmission. Cluster access ends Aug 15, so the link cannot live there. Two candidate homes, different tradeoffs. Decide after testing both, submit one.

## Option A: laptop behind a cloudflared tunnel

Everything already runs here. RTX 4060 8GB holds the 0.6B Q8 (about 1.2GB), the two guard models (about 2GB) and the e5 encoder together.

Stack, boot order:

1. llama-server: `tools\llama\llama-server.exe -m models\Qwen3-0.6B-Q8_0.gguf -ngl 99 -fa 1 -c 2048 --port 8001 --no-webui`
2. Guard sidecar in its own venv (transformers 4.49 pin, same as the cluster): `guard-env\Scripts\python -m uvicorn vaani.guard_service:app --port 8002` with `VAANI_GUARD_DEVICE=cuda`
3. App: `uvicorn vaani.server:create_default_app --factory --port 8000` with `VAANI_CORPUS=data/corpus/hin_val VAANI_INDEXES=indexes/hin_val VAANI_GENERATION_URL=http://127.0.0.1:8001/v1 VAANI_GUARD_URL=http://127.0.0.1:8002` and the Sarvam key from .env
4. Tunnel: `cloudflared tunnel --url http://127.0.0.1:8000` (install first: `winget install Cloudflare.cloudflared`)

Still to build for this: the local guard-env (uv venv, transformers 4.49, cu128 torch, about 3GB disk, one-time 2GB model download) and the cloudflared install.

Strengths: real numbers. Generation at 77ms, the same streaming UI the video shows, mic to answer under a second.

The honest problems:

- A quick tunnel gets a random trycloudflare.com URL that changes every restart. The form is submitted days before judging; one laptop reboot and the submitted link is dead. A stable named tunnel needs a Cloudflare account with a domain we do not have.
- The laptop must stay powered, awake and online from submission until judging ends. Sleep mode, a wifi drop or a Windows update kills the link.

Mitigations if we pick A: disable sleep and updates for the window, keep cloudflared and the stack under a supervisor script that restarts on boot, and only submit the URL on the final day so restarts before that are free.

## Option B: Hugging Face Space (docker, free CPU)

Push a Docker Space that bundles the app, the passage plus bm25 index (about 1.1GB), the corpus parquet (350MB), e5, and llama.cpp CPU with the Q8 or Q4 GGUF. Free tier is 2 vCPU and 16GB RAM, which fits.

Strengths: the URL is stable and always up. Nothing at home has to stay running. Sarvam REST and the websocket both work from a Space.

The honest problem: CPU generation for a 0.6B runs 1 to 2 seconds an answer. The under-200ms story then rests on the committed benchmark reports and the demo video, not on the link itself. Retrieval, guards, abstention and the whole UI still behave correctly at CPU speed, and extractive answers stay fast.

## Recommendation

Build both, they share everything but the host. Submit the Space URL in the form because the no-resubmission rule punishes a dead link far more than a slow one. Put the tunnel URL in the README as "fast mode" and bring the laptop up live for any interactive judging. If testing shows the Space too painful even for a patient judge, flip the decision and accept the uptime babysitting.

## Test checklist before the form goes in

- Voice roundtrip from a phone on mobile data, not the home network: mic, partials, tokens, answer, waterfall.
- The refusal case (ask something the corpus cannot know) and a Hindi voice query.
- Text fallback box, and the clip path on a browser without AudioWorklet.
- Sarvam spend ledger after the tests: budget is 100 rupees, each voice query costs well under one.
- Kill and restart the stack once; confirm the link recovers without hand-holding.

## Order of work

1. Local guard-env plus one end-to-end laptop run with guards on GPU.
2. cloudflared install, quick tunnel, phone test through the tunnel.
3. Space Dockerfile, push, same phone test against the Space URL.
4. Decide, then wire the chosen URL into the README and the form.
