# Live link plan (v2, after the codex review and solution pass)

The review killed v1's assumptions: quick tunnel URLs rotate on restart, new HF Docker Spaces need a paid account, free Spaces sleep after 48h, the realtime Sarvam path is unverified against current docs, and a public voice endpoint with no controls can burn the 100 rupee balance in about ten minutes. The architecture that survives all of that:

```
vaani.pages.dev  (permanent, this is the submitted URL)
    -> Cloudflare Worker: turnstile, per-IP limits, spend allowance, routing
        -> primary backend  (HF Space paid track / laptop funnel free track)
        -> laptop RTX fast mode (optional, streaming lives here)
            -> Sarvam STT
```

## The front door

Cloudflare Pages serves the actual UI at a permanent pages.dev address. A Worker on the same address proxies /api/* to whichever backend is alive and holds the abuse gate. The submitted URL never changes; backends can die, rotate or get swapped behind it. When every backend is down the Worker serves a status page with the demo video and a note, so a judge never hits a dead link. Free tier covers this: static traffic unlimited, 100k Worker requests a day.

The Worker and the backend share a random origin secret so nobody can call the backend directly and bypass the gate. The Sarvam key lives only in the backend's secret store, never in browser code.

## The money decision (Kartik decides, nothing proceeds without it)

- Paid track, about 1200-1300 rupees total: HF PRO one month ($9) unlocks a protected Docker Space on CPU Basic (free per hour). Optionally CPU Upgrade ($0.03/hr, about $5 for judging week) to kill sleeping and cold starts. This is the always-on option.
- Free track, 0 rupees: no Space. The laptop is the only backend, reached through Tailscale Funnel (free, stable .ts.net name, survives reboots with --bg). The Worker front door still protects the submitted URL and serves the fallback status page whenever the laptop is asleep or offline. The demo goes down when the laptop does; the link never dies.

Either way the Pages URL is what goes in the form. The track choice only changes what sits behind it.

## Voice path on the public link

Push-to-talk HTTP, not streaming. The existing /api/voice clip path already does exactly this and is verified against the real Sarvam REST API. Limits enforced twice, once in the Worker and once in the app: 15 second recordings, about 1MB upload cap, one Sarvam call at a time, ten voice turns per IP per hour, Turnstile before the first voice request, and a persistent public allowance of roughly 40 minutes (about 20 rupees) tracked in a Durable Object. When the allowance runs out, voice declines politely; text RAG keeps working. The remaining 80 rupees stay reserved for development, the demo video and judges.

Streaming with speculative retrieval stays as laptop fast mode. The realtime protocol must be validated against Sarvam's current docs (GET /speech-to-text/ws, saaras:v3, final-per-utterance events) with real audio before the demo relies on partials existing at all. That check happens on cluster day with the mic already in hand.

## CPU reality on the Space (paid track)

Generation gets 5-8 seconds of timeout on CPU, not 150ms, or every request silently falls back to extractive. Q4 GGUF on the Space, Q8 stays on the laptop. Concurrency one. Benchmark inside the real Space before advertising any number; treat 1-5 seconds as the estimate until then. Guards ship with the Space with 1-2 second deadlines, or the Space gets labeled CPU compatibility mode; either way unchecked answers say so, never pretend to be graded. The 200ms story rests on the committed cluster reports and the video, and the UI says which mode it is running.

## Licensing

Protected Space (source not clonable), corpus fetched from the original HF repository at build time, no corpus browse or download endpoints, only the short passages each answer needs, attribution in the app. The GitHub repo already excludes corpus and models.

## Already true, worth not redoing

- The laptop already holds byte-verified copies of every artifact the cluster has (passage+bm25 index, corpus, GGUFs); guard models re-download from public HF repos. Checksums get recorded tonight, which completes the two-locations requirement.
- App-side enforcement is half built and parked in git stash ("wip budget caps"): ledger spend ceiling, upload byte cap, utterance cap, session concurrency, origin-token check, env-configurable generation and guard timeouts. Unstash when implementation resumes; it is the Space-side half of the budget gate.
